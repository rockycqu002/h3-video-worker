# H3 视频 worker 测试报告（RunPod Serverless · RTX 4090）

## 1. 结论

1. **四种模式都能用**：T2V、I2V、FL2V（首尾帧，走 skill 改写）、跳过改写均已实测；T2V / I2V / FL2V 在最长的 15 s 下都成功，进程内存峰值 ≤ 18.6 GB（v0.1.3 + `--fast-disk` 起）。
2. **找到并修复了 OOM**：RunPod 4090 worker 的容器内存上限是 **43,869 MiB**。ComfyUI 0.37 默认把约 37 GB 权重副本常驻在进程内存里，
   5 s / 8 s 视频的峰值已经贴着上限，10 s 视频在 VAE 解码时被系统 OOM 杀掉（exit -9）。加上 ComfyUI 参数 `--fast-disk` 后，
   进程内存峰值降到 **7–18 GB**，生成速度不变。v0.1.4 起这是默认参数。
3. **早期的 “ComfyUI died” 有两个叠加原因**：真 OOM（原因 2），以及 v0.1.0/0.1.1 的存活检查只等 5 s HTTP 回应，慢主机上会误判。v0.1.2 已改为检查进程本身。
4. **耗时随时长超线性增长**：5 s ≈ 166 s，8 s ≈ 326 s，10 s ≈ 510–540 s，15 s ≈ 1009 s（约 17 分钟）。endpoint 超时已从 900 s 调到 1800 s。
5. **成本**（worker 已热，按本账户 4090 serverless 实际费率 $0.000306/s）：5 s ≈ **$0.055**、8 s ≈ $0.10、10 s ≈ $0.16、15 s ≈ $0.31；零散请求每条再加约 $0.03。
6. **主机差异大**：同样读 42 GB 权重，快的主机 41–44 s，慢的 548 s；慢主机上生成也会变慢（一次 5 s 视频用了 812 s）。目前只能靠超时和重试兜底。

## 4. OOM 根因分析

**现象**：#6 在 5 s 视频生成中途报 “ComfyUI died”；#11 的 10 s 视频被 OOM 杀掉；#9、#10 的内存峰值离上限只差几 MiB。

**数据**（v0.1.3 内存采样器，每 2 秒一次，区分进程内存 anon 和文件缓存 file）：

- 容器上限 `memory.max` = 43,869 MiB（标称 46 GB）。
- 不加 `--fast-disk` 时：文本编码器和 DiT 加载完成后，anon 在约 30 s 内升到 **37,331 MiB** 并一直保持，这是 ComfyUI 的 dynamic VRAM
  为了随时换入显存而在内存里保留的权重副本。生成末尾加载视频 / 音频 VAE 做解码，anon 再涨 2.5–6 GB（视频越长越多）：
  5 s → 39,990，8 s → 40,769，10 s → 43,475 → 被杀。
- 加 `--fast-disk` 后：权重改为从磁盘映射按需读取，暂不用的部分只以文件缓存存在，内核在压力下可以回收。anon 峰值：
  5 s 7,173–17,842，8 s 15,766，10 s 12,211–12,648，15 s 17,839。总占用仍可能接近上限，但那部分是可回收的文件缓存，不会触发 OOM。

**速度影响**：几乎没有。同一主机热启动对比：5 s 170.7 → 165.7 s，8 s 330.6 → 325.7 s。

**#6 的归因**：#6 发生在 v0.1.1，当时的存活检查是 “5 s 内收不到 `/system_stats` 回应就算死亡”，既可能是真 OOM（5 s 本就贴着上限），
也可能是慢主机上的误判（同类主机 #7 生成用了 812 s）。v0.1.2 把存活检查改成看进程状态，v0.1.3 加了死亡报告（退出码、`oom_kill`
次数、分阶段内存峰值、ComfyUI 日志末行）；之后再出现的 #11 由报告确认是 OOM（exit -9）。

**修复**：v0.1.4 默认 `H3_COMFY_ARGS="--reserve-vram 1 --disable-nvml-pressure --fast-disk"`。

## 6. 发现的问题与处理

| 问题 | 版本 | 处理 |
|---|---|---|
| 内存统计读的是宿主机 `/proc/meminfo` | v0.1.0 | v0.1.1 改读容器 cgroup；v0.1.3 支持 cgroup v1/v2 并加分阶段采样 |
| 存活检查靠 5 s HTTP，慢主机上误判 “died” | v0.1.0–0.1.1 | v0.1.2 改为检查进程，HTTP 最多容忍 180 s 无回应 |
| 10 s 视频 OOM（容器上限 43.9 GB） | ≤ v0.1.3 | v0.1.4 默认 `--fast-disk` |
| 15 s 视频需要约 17 分钟，超过 900 s 超时 | ≤ v0.1.3 | v0.1.4：worker 截止 1740 s，endpoint 超时 1800 s |
| RunPod 更新 template 后不替换空闲的旧 worker | 平台行为 | 发布新版本后把 max workers 设 0 再设回，确保新请求落在新镜像上（已写入部署流程） |
| `networkVolumeIds` 要求传对象 | 平台 API | 单机房时用 `networkVolumeId` |
| endpoint 刚改完配置时 `/run` 返回 HTTP 409 Conflict | 平台行为 | 调用方对 409 / 429 / 5xx 做退避重试（已写入 `API_CALLER.md`） |
| 慢主机读盘慢（42 GB 读 548 s） | 平台差异 | 暂无法选择主机；靠超时 + 调用方重试兜底。量大后可考虑多机房 Volume |
